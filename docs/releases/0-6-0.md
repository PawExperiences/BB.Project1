## Release steps

1. [manual] Pre-flight: confirm there is application source to release - This release's git range (3d812d4..8e02c96) contains only 'chore: reset repo' x2, 'chore: reset for the next e2e project', and 'ci: scaffold BuildBoard build workflow' — diffstat is empty and no tasks are bundled. Before tagging, check out 8e02c96 and confirm CMakeLists.txt and src/ actually exist: `git show 8e02c96 --stat` and `git ls-tree -r 8e02c96 --name-only`. If they don't exist, STOP — do not publish an empty release; route this back to Grooming/Coder for the prime tester source. If they do exist (the diffstat/task feed simply wasn't populated for this run), proceed.
2. [manual] Confirm the CI workflow matches the shipped toolchain - Open .github/workflows/build.yml on the release commit and compare its build command / artifact path against the project's Build resource config (toolchain-cpp: image gcc:14-bookworm, artifact_path build). This release's only functional change is scaffolding that workflow (commit 5e3fc19), so no drift is expected — confirm it, don't assume it. If a future release changes the compiler image, build command, or artifact path, update the Build resource config in BuildBoard (never hand-edit the workflow file) so it re-scaffolds build.yml; BuildBoard owns this file and will overwrite manual edits.
3. [automated] Build locally to verify build parity with CI - Run `release/scripts/release.{py,sh,ps1}` (its build stage), or manually: `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build` — ideally inside `docker run --rm -v $PWD:/src -w /src gcc:14-bookworm bash -c "cmake -S . -B build && cmake --build build"` to match the CI image exactly. Confirms the workflow's build actually produces the build/prime_tester executable before anything is tagged.
4. [automated] Tag the release - release script creates annotated tag `0.6.0` (matches the delivery resource's tag_template `{version}` — no 'v' prefix) at the release commit and pushes it to origin: `git tag -a 0.6.0 -m 'Release 0.6.0' && git push origin refs/tags/0.6.0`. Additive only — never force-push or replace an existing tag.
5. [automated] Publish the GitHub Release and upload the build artifact - release script (or BuildBoard's one-click Release -> Auto flow) creates the GitHub Release on PawExperiences/BB.Project1 tagged 0.6.0, titled 'e2e prime tester cc 0.6.0', body = releaseNotes, and uploads the packaged build/ output as build-0.6.0.zip. Idempotent: re-running reuses an existing tag/release instead of erroring.
6. [manual] Verify the published release - On the GitHub Releases page, confirm tag 0.6.0, the asset is attached, and the referenced CI run is green. Download the asset and smoke-test: `./prime_tester 97` -> `97 is prime` (exit 0); `./prime_tester abc` -> `not a number: abc` on stderr (exit 1).
7. [manual] Announce - Share the release notes wherever the team tracks releases. No chat/notification resource is bound to this project in the given inputs, so this is a manual post; BuildBoard's own 'announce' stage will handle it automatically if/when such a resource is configured.

## Rollback

This is the first release, so there is no prior version to fall back to, and protected-remote-state rules forbid deleting the 0.6.0 tag, the GitHub Release, or any commit history. If a defect is found after publishing: (1) leave the 0.6.0 tag and release in place; (2) if the release notes or asset are wrong, edit the existing GitHub Release in place (title/body/asset) rather than deleting it — edits are additive; (3) cut a fix-forward patch release (0.6.1) with the correction, and if 0.6.0 should no longer be recommended, mark it 'pre-release' via an in-place edit rather than removing it; (4) if the CI workflow itself is broken, fix it by updating the Build resource config in BuildBoard (which re-scaffolds .github/workflows/build.yml) or via a normal commit + PR — never hand-edit or delete the managed workflow file. No data/schema migrations exist to roll back.
