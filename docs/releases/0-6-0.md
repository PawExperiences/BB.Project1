# e2e prime tester cc 0.6.0 (0.6.0)

## prime_tester 0.6.0

The first shippable build of the prime tester: a self-contained C++17 console application,
built with CMake and depending on nothing beyond the standard library. It answers "is this
number prime?" for numbers given as arguments or piped in on stdin, and it enumerates a whole
range with `--upto N` using a sieve of Eratosthenes. Bad input never truncates a run - a token
that is not an integer (or does not fit in `long long`) is reported on stderr as
`not a number: <token>`, the remaining input is still processed, and the program exits 1. Before
this release the repository had no `CMakeLists.txt` and nothing in it built; 0.6.0 establishes
the canonical build, the one executable, and a CTest suite over the sieve boundaries.

### Highlights

- **One command to build, one binary to run.** `cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build` produces `build/prime_tester` on a clean checkout, with no third-party dependency.
- **Two invocation modes.** `./build/prime_tester 7 8 1 -3 2` tests the arguments in order; with no arguments it reads one integer per line from stdin until EOF.
- **Range mode.** `./build/prime_tester --upto 30` prints every prime up to 30, one per line. `--upto 1000000` emits exactly 78498 lines.
- **Errors are diagnostics, not aborts.** Bad tokens go to stderr, good tokens still get answered, and the exit status is 1 if anything was rejected - 0 otherwise, including for empty input.
- **Checkable by a human.** `ctest --test-dir build` runs the sieve boundary tests, and the README's eight-row worked-examples table is a paste-and-compare acceptance script.

### Build and run

```sh
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build

./build/prime_tester 7 8 1 -3 2      # arguments mode
printf '11\n12\n' | ./build/prime_tester   # stdin mode
./build/prime_tester --upto 30       # range mode
```

Or use the bundled helper, which builds first if it has to and passes everything through:

```sh
./release/scripts/run.sh --upto 30
python3 release/scripts/run.py --upto 30
powershell -File release\scripts\run.ps1 --upto 30
```

### Verify

```sh
ctest --test-dir build --output-on-failure
```

### Exit-code contract

| status | meaning |
|---|---|
| `0` | every token parsed and was answered (empty input counts as a clean run) |
| `1` | at least one token was rejected; each was reported on stderr as `not a number: <token>` |

Diagnostics for rejected tokens and for a bad `--upto` value go to **stderr**, so they do not
appear when stdout is redirected.

## [0.6.0] - 2026-08-22

First tagged release of the C++ prime tester. Before this release the repository had no
`CMakeLists.txt` and nothing in it built; 0.6.0 establishes the canonical CMake build, the
one executable the project grows from (`build/prime_tester`), and the two primality
primitives (`is_prime`, `primes_up_to`) everything later is measured against.

### Added

- **CMake build** (`CMakeLists.txt`, commit `363695e`) - `cmake_minimum_required(VERSION 3.16)`,
  `project(prime_tester ... CXX)`, `CMAKE_CXX_STANDARD 17`, a single executable target
  `prime_tester`, and no third-party dependency (no `find_package` for external libs, no
  `FetchContent`). `cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build`
  succeeds on a clean checkout and produces `build/prime_tester`.
- **`bool is_prime(long long)`** (`src/prime.h`, `src/prime.cpp`, commit `363695e`) - trial
  division to the square root with the 6k+/-1 optimisation. Every `n < 2` is not prime
  (negatives, 0 and 1), 2 and 3 are prime, every even `n > 2` is not. Verified against the
  odd composites 9, 25, 91 (7x13) and 1000001 (101x9901), so the candidate loop skips no
  real factor.
- **Single-number CLI** (`src/main.cpp`, commit `363695e`) - numbers passed as arguments are
  tested in input order; with no arguments the program reads one integer per line from stdin
  until EOF. Each value prints exactly `<n> is prime` or `<n> is not prime` on stdout.
- **Tolerant input handling** (`src/main.cpp`, commit `363695e`) - a token that is not an
  integer, or one that does not fit in `long long`, is reported on **stderr** as
  `not a number: <token>` and does **not** abort the run; the program processes the
  remaining input and then exits **1**. A clean run - including empty input - exits **0**.
- **Sieve of Eratosthenes** (`src/sieve.h`, `src/sieve.cpp`, commit `f160c5e`) -
  `std::vector<long long> primes_up_to(long long n)` returns every prime `<= n` in strictly
  ascending order using a composite-marking array. `primes_up_to(100)` has 25 entries ending
  at 97; `primes_up_to(1000000)` has 78498 entries ending at 999983. `n < 2` returns an empty
  vector without crashing or over-allocating.
- **`--upto N` range mode** (`src/main.cpp`, commit `f160c5e`) - prints every prime up to `N`,
  one per line, and exits 0. `N` below 2 prints nothing and still exits 0. A missing or
  non-integer `N` writes a diagnostic to stderr, prints nothing on stdout, and exits
  non-zero.
- **CTest suite** (`tests/sieve_test.cpp`, commit `f160c5e`) - covers the small range, the
  2/3 boundaries, `n < 2`, and the 100 / 1000000 counts; registered with CTest (test name
  `sieve_boundaries`) and run with `ctest --test-dir build`.
- **README worked-examples table** (`README.md`, commit `cbfd86c`) - one markdown table with
  Command / Expected stdout / Exit status columns and eight rows (a prime, a composite, 0, 1,
  a negative, a non-numeric token, empty stdin, `--upto 30`), each cell transcribed from an
  actual run of the built binary, plus a note stating which cases write to stderr rather than
  stdout.

### Changed

- **The CMake target grew a second source and a test hook** (commit `f160c5e`) - the first
  card deliberately shipped one executable from `src/main.cpp` + `src/prime.cpp` with no
  `enable_testing()`/`add_test()`; the sieve card added `src/sieve.cpp` to the same single
  target and registered `tests/sieve_test.cpp` with CTest. `ctest --test-dir build` is now
  part of the build contract, superseding the first card's "no test framework" constraint.
- **Trial division and the sieve coexist** (commit `f160c5e`) - the sieve serves the range
  path only. `is_prime(long long)` keeps its signature and still serves the single-number and
  stdin paths; `src/prime.h` / `src/prime.cpp` were not modified by the sieve card.
- **`README.md` became the project's manual acceptance script** (commit `cbfd86c`) - it now
  carries the exact build commands, the executable path under `build/`, both invocation
  modes, the test command and the exit-code contract, so a first-time reader can build, run
  and check the app without opening a source file.

### Fixed

- Nothing. 0.6.0 is the first tagged release of this project, so there is no earlier released
  behaviour to correct.

## Rollback

This release ships a standalone console executable with no data store, no schema and no runtime dependency, so rollback is entirely about the published artefact and the CI build config - nothing to un-migrate.

Protected-state rule first: do NOT delete or force-move the `v0.6.0` tag, the GitHub release, the uploaded asset, or any workflow file. Roll forward or hide in place instead.

1. Stop the bleeding (in place, reversible). Ask a maintainer to mark the release as a draft or a pre-release so it stops being served as `latest`:
   `gh release edit v0.6.0 --draft` (or `--prerelease`). This edits the release; it does not delete it. Record who approved it.
2. Restore the previous consumer state. There is no previous prime_tester release to roll back to (PREVIOUS is None). Consumers who need the old repository artefact must pull the last Maven/JAR build from before commit `363695e` - it is not republished by this rollback.
3. Revert the code with a new commit, never a history rewrite. On a fresh branch off `main`:
   `git revert -m 1 493dc39 1c28b56 613bccf` (the three merge commits, newest first), then open a PR and merge it. If only one card is at fault, revert only its merge commit: `#384` = `493dc39` (README), `#383` = `1c28b56` (sieve + `--upto`), `#382` = `613bccf` (console app + CMake build).
4. Revert the CI build resource. If the build resource config was switched to the CMake command/artifact path for this release and the revert removes `CMakeLists.txt`, set the build resource back to the toolchain the reverted tree actually builds with, and let BuildBoard re-scaffold `.github/workflows/build.yml`. Do not hand-edit or delete the workflow file. A reverted tree with a CMake build config produces a red pipeline on the very next build.
5. Re-run the BuildBoard build of `main` and confirm it is green against the reverted tree.
6. Ship the correction as a new version (0.6.1), never by re-tagging `v0.6.0`. Re-run `release/scripts/release.sh --version 0.6.1`.
7. Announce the withdrawal on the same Discord publish target used for the release, linking the revert PR.

Local-only cleanup is unrestricted: `rm -rf build dist` and `git tag -d v0.6.0` on a developer machine are fine; the prohibition is on the remote.
