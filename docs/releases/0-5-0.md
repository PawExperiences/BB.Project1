# e2e space invaders cc 0.5.0 (0.5.0)

## e2e space invaders cc 0.5.0

The first playable build of our browser-based Space Invaders clone. No install, no build step, no server required: clone the repo and open `index.html` in a browser to play.

### Highlights
- Open `index.html` directly (`file://`) and start playing immediately - zero build, zero dependencies.
- A smooth, fixed-timestep (60Hz) game loop that stays stable even after your tab sits in the background for a while.
- A full Title -> Playing -> Game Over flow, controlled entirely with ENTER.
- A live on-canvas HUD tracking score, lives, and hi-score.
- A keyboard-controlled player ship with movement and shooting.

Invader waves and collision-driven scoring are on the way in an upcoming release.

## [0.5.0] - 2026-08-10

First tagged release of the project (PREVIOUS: None).

### Added
- Static, zero-build game shell: `index.html` hosts a 768x896 `<canvas>` on a dark page; opens directly via a `file://` URL with no server or build step. (`index.html`, `gameConfig.js`)
- Shared numeric constants module `gameConfig.js` exporting `CANVAS_WIDTH` (768), `CANVAS_HEIGHT` (896), `PLAYER_SPEED` (200), `BULLET_SPEED` (500), and `STARTING_LIVES` (3).
- Fixed-timestep game loop in `game.js`: 60 updates/sec with distinct update and render phases, and a clamped accumulator so resuming a backgrounded/restored tab never fires a burst of catch-up updates.
- Three-scene state machine driven entirely by ENTER, never reloading the page: **Title** ("SPACE INVADERS" / "Press ENTER to start") -> **Playing** -> **Game Over** ("GAME OVER", final score, "Press ENTER to restart") -> back to Title.
- On-canvas HUD (score, lives) rendered every frame during Playing, backed by an exported `hudState` object (`score`, `lives`, `hiScore`) so later gameplay cards can read/mutate it without owning scene/HUD logic.
- Game Over triggers automatically when `hudState.lives` reaches 0.
- Keyboard-controlled player ship and shooting, added in `input.js` / `player.js` (commit `1dc86a0`, "Keyboard input and the player ship", PR #198). ## Rollback

v0.5.0 is the first tagged release, so there is no prior version to fall back to, and per policy the release tag/GitHub Release must never be deleted or force-pushed. If a defect is found post-publish: (1) leave the 'v0.5.0' tag and GitHub Release in place - edit the existing release in place (GitHub allows editing a published release's body/pre-release flag without deleting it) to mark it as having a known issue, with a short note and a link to the fix; (2) fix forward on 'main' (prefer 'git revert <sha>' for a clean, auditable revert over hand-editing), then cut a new patch tag/release (e.g. 'v0.5.1') using the same release/scripts/release.* script - never re-use or overwrite the 'v0.5.0' tag; (3) because this is a static, zero-backend client app with no persisted data, end-user 'rollback' just means pointing players at the previous release asset/tag (or the last-known-good commit) until 'v0.5.1' ships - there is no server-side deploy to revert and no data migration to reverse.
