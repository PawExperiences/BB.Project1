# e2e changelog writer 0.1.0 (0.1.0)

## e2e changelog writer v0.1.0

This is the first release of e2e changelog writer. It establishes the project's own release process rather than shipping application code: a Keep a Changelog-formatted `CHANGELOG.md`, a maintainer checklist for cutting future releases (`RELEASING.md`), and a contributor guide that teaches how to write correctly-categorized, user-facing changelog entries (`CONTRIBUTING.md`).

### Highlights
- `CHANGELOG.md` added, following Keep a Changelog 1.1.0 and Semantic Versioning, with an empty `Unreleased` section (all six standard subheadings) ready for future work, and this release recorded under `## [0.1.0] - 2026-01-01`.
- `RELEASING.md` added: a 5-step checklist maintainers follow for every future release, including how to correct a tag that was pushed by mistake.
- `CONTRIBUTING.md` added: documents all six Keep a Changelog categories with one example each, and teaches contributors to phrase entries from the user's point of view rather than the commit's (with a before/after example).
- Documentation-only release: no application code, dependencies, schema, or CI/workflow changes ship in v0.1.0.

## Release steps

1. [automated] Verify CI is green for the release commits - Run `gh run list --branch main --limit 5 --json headSha,conclusion` and confirm the workflow run(s) covering commits 178204a (#306, CHANGELOG and release checklist) and 7dae08f (#307, contributing guide) show conclusion=success. Do not proceed to tagging if either is failing or still pending.
2. [manual] Resolve the task-3 scope mismatch - The bundled task 'A worked second release' describes creating a `## [0.2.0] - 2026-03-01` section in CHANGELOG.md, but no commit for it appears in the supplied git log/diffstat for this 0.1.0 range, and it targets a different version than this release. A human must confirm with the project owner whether it was mistakenly bundled into 0.1.0 (defer its content to the real 0.2.0 release) or whether the diff supplied to this runbook is incomplete (re-pull it before continuing). This runbook's changelog and notes exclude task 3's content pending that confirmation.
3. [automated] Verify CHANGELOG.md, RELEASING.md, and CONTRIBUTING.md against their acceptance criteria - Check heading structure: CHANGELOG.md must show an intro identifying Keep a Changelog 1.1.0 and SemVer, then `## [Unreleased]` with `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed`, `### Security` (all empty, in that order), then exactly one `## [0.1.0] - 2026-01-01` section containing only `### Added` with a single bullet stating the project was started. Confirm RELEASING.md is a 5-item numbered list, one imperative sentence per item, covering version selection, moving entries, tagging, pushing, and correcting a bad tag. Confirm CONTRIBUTING.md documents all six Keep a Changelog categories, one example entry each, plus a before/after user-facing-wording example, and contains no general dev-setup, PR-process, or code-style content.
4. [automated] Confirm the CI build workflow matches this release's toolchain - Diff `.github/workflows/build.yml` (owned and re-scaffolded by BuildBoard from the build resource's command and artifact_path) against the build resource's currently configured values. This release changes no code, build command, or artifact -- it is documentation-only -- so the workflow should be unchanged from the last known-good version. If it has drifted, update the build resource's command/artifact_path config (not the workflow file) so it re-scaffolds correctly, then re-run this check before continuing.
5. [automated] Freeze the release notes artifact - From a clean checkout of main, write this runbook's releaseNotes markdown to `release/RELEASE_NOTES.md` (create the `release/` directory if absent). This file is consumed by `gh release create --notes-file` in the release script; it is a build/release-time artifact, not something committed as project documentation.
6. [automated] Run the release script - From a clean, up-to-date main checkout, run `python3 release/scripts/release.py` (or the .sh/.ps1 equivalent) with `RELEASE_VERSION=0.1.0`. It verifies a clean working tree on main, creates annotated tag `v0.1.0`, pushes the tag to origin, and runs `gh release create v0.1.0 --title v0.1.0 --notes-file release/RELEASE_NOTES.md`. The script is idempotent -- safe to re-run if interrupted at any point.
7. [manual] Verify the published release - Open the new v0.1.0 release on GitHub and confirm: the tag points at the commit containing both #306 and #307, the title and notes rendered correctly, and no unintended assets were attached. This is a manual sanity check of rendered output, not a scriptable assertion.

## Helper scripts (committed under release/scripts/)

- **release** `release/scripts/release.py` (python) -- Idempotently tags the current main commit as v0.1.0 (or RELEASE_VERSION env var), pushes the tag to origin, and publishes the GitHub Release using release/RELEASE_NOTES.md as the notes body; run once CHANGELOG.md/RELEASING.md/CONTRIBUTING.md are verified and CI is green.
- **release** `release/scripts/release.sh` (sh) -- POSIX sh equivalent of release.py: idempotently tags main as v0.1.0 (or RELEASE_VERSION env var), pushes the tag, and publishes the GitHub Release from release/RELEASE_NOTES.md; run once CHANGELOG.md/RELEASING.md/CONTRIBUTING.md are verified and CI is green.
- **release** `release/scripts/release.ps1` (powershell) -- PowerShell 5.1-compatible equivalent of release.py: idempotently tags main as v0.1.0 (or env:RELEASE_VERSION), pushes the tag, and publishes the GitHub Release from release/RELEASE_NOTES.md; run once CHANGELOG.md/RELEASING.md/CONTRIBUTING.md are verified and CI is green.

## Rollback

This is a documentation-only release with no code, schema, or runtime changes, so rollback risk is minimal. Per protected-remote-state rules, never delete the v0.1.0 tag, delete or unpublish the GitHub Release, or force-push/rewrite history to undo it. If a defect is found in the shipped docs (e.g. a malformed CHANGELOG.md heading): (1) fix the file(s) on main via a normal PR -- do not amend or force-push the tagged commit; (2) cut a corrective patch release v0.1.1 following RELEASING.md's checklist, filing the fix under Fixed; (3) edit (never delete) the existing v0.1.0 GitHub Release description to add a note pointing readers to v0.1.1. If the tag was cut against the wrong commit entirely, follow RELEASING.md's own tag-correction step: push a new corrected tag/release and mark the erroneous one as superseded in its notes -- do not delete the erroneous tag or release.
