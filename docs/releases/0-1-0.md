# e2e standup poster 0.1.0 (0.1.0)

## e2e standup poster 0.1.0

First release of the e2e standup poster: a small, static, backend-free Vite + React + TypeScript app that renders a single hardcoded "standup card" — a date heading followed by Yesterday, Today and Blockers sections. This release also ships a reusable presentational `StandupCard` building block (Done / In Progress / Blocked, driven entirely by props) and a shared `Empty` placeholder used wherever a section has nothing to show, alongside the App-level scaffold that puts a hardcoded card on screen today.

### Highlights
- Static, no-backend standup card: date heading + Yesterday / Today / Blockers, each a bulleted list from one hardcoded object literal in `App.tsx`.
- An empty Blockers list reads as a muted "none", not a confusing blank list.
- New `StandupCard` component (Done / In Progress / Blocked from props), Tailwind-styled, with a Vitest + Testing Library test.
- New shared `Empty` placeholder component with a documented prop contract and a README usage example.
- README covers install (`npm ci`) and build (`npm run build` → `dist/index.html`).

### Known gaps
- `StandupCard` is not yet wired into `App.tsx`, and its props/usage are not yet documented in the README — both are candidates for a follow-up release.

1. [manual] Verify the release commit matches the release's file scope - Run `git show <candidate-HEAD> --stat` and `git ls-tree -r <candidate-HEAD> --name-only` on the real repository. ## Rollback

This is a static, backend-free frontend with no data store, so a rollback never touches user data. Per the protected-remote-state rule, never delete the v0.1.0 tag, the GitHub Release, or any commit — only additive/in-place fixes are allowed.

1. If dist/ has already been deployed to a static host, redeploy the previous known-good artifact (there is none, since this is the first release) or point the hosting target back to a pre-release state (e.g. a maintenance/empty page).
2. Edit the GitHub Release for v0.1.0 in place — mark it as a pre-release and add a note at the top of its body explaining it was rolled back and why. Do not delete or unpublish it.
3. Fix the underlying issue on main, then cut a new patch release (e.g. v0.1.1) using the same release/scripts/release.* script. Do not force-push or rewrite the v0.1.0 tag or history.
4. If the CI build workflow needed to change while chasing the issue, revert the build resource's command / artifact_path to its last-good values so .github/workflows/build.yml re-scaffolds back to the working configuration.
