# e2e ticket mirror 0.1.0 (0.1.0)

## e2e ticket mirror v0.1.0

First release of the e2e ticket mirror: a minimal, dependency-light Next.js 14 (App Router, TypeScript) scaffold that renders a static, kanban-style view of six tickets sourced from `data/tickets.json`. There is no database and no API route -- the whole app is buildable end-to-end with `npm ci && npm run build` -- and the ticket-grouping logic lives in one tested module (`lib/group.ts`) rather than being duplicated inline.

### Highlights
- Three fixed status columns -- **To Do**, **In Progress**, **Done** -- each with a live ticket count.
- Grouping centralized in `lib/group.ts` (`groupByStatus`), covered by a Vitest suite: fixed bucket order, stable partitioning, safe handling of unrecognized statuses, and the empty-array case.
- Right-aligned assignee chip on every ticket row (`app/Chip.tsx`), with a clearly muted "Unassigned" state when no assignee is set.
- README documents the exact `tickets.json` shape with a full example ticket.
- Zero runtime surface beyond Next.js/React: no database, no API routes, no external services.

### Verify it yourself
```
npm ci
npm run build
```
Both must exit 0 from a clean checkout.

## Rollback

This is the initial release (v0.1.0); there is no prior version to fall back to. If a defect is found after publishing:
1. Do not delete the v0.1.0 git tag or the GitHub Release -- deleting/removing remote state is out of scope for this role and against BuildBoard policy.
2. Mark the GitHub Release as a pre-release in place (`gh release edit v0.1.0 --prerelease`) to signal it should not be treated as production-ready, and note the reason in the release body -- this is an in-place edit, not a deletion.
3. If the app was started via release/scripts/run.*, stop that process; there is no deployed environment to redirect traffic away from for this release.
4. Groom the fix, then cut it as v0.1.1 following this same runbook once it passes npm run build and the Vitest suite, and point consumers at v0.1.1 instead.
5. Because the app is stateless (data/tickets.json is static, no database, no migrations), rollback carries no data-loss risk -- it is purely a matter of which tagged build is considered current.
