# e2e prime tester 0.1.0 (0.1.0)

## e2e prime tester 0.1.0

This is the initial public release of **prime tester** — a self-contained, dependency-free C++17 console application that determines whether integers are prime numbers.

The application accepts input as command-line arguments or from stdin (one token per line), prints `<n> is prime` / `<n> is not prime` to stdout for each valid integer, reports invalid tokens to stderr, and exits with code `0` (all inputs valid) or `1` (at least one invalid token). It is built with CMake 3.16+ and ships a GitHub Actions CI workflow managed by BuildBoard.

### Highlights
- **New app:** `prime_tester` executable built from five canonical source files (`CMakeLists.txt`, `src/prime.h`, `src/prime.cpp`, `src/main.cpp`, `README.md`).
- **6k±1 optimisation:** `is_prime` uses efficient trial division; correct for all `long long` values including edge cases (negatives, 0, 1, 2, 3, overflow tokens).
- **Dual input mode:** command-line args _or_ stdin — no external dependencies, no install step.
- **CI baseline:** BuildBoard-scaffolded `build.yml` workflow confirms every commit builds cleanly.
- **Exit-code contract:** strictly defined; partial failures (mixed valid/invalid tokens) still process all input.

## Release steps

1. [manual] Confirm CI build workflow currency - Open `.github/workflows/build.yml` and verify the build command is `cmake -B build && cmake --build build` and the artifact path is `build/prime_tester`. If the toolchain, build command, or artifact path changed, update the BuildBoard build resource config (so the workflow re-scaffolds) before proceeding. This step is manual — it requires human inspection.
2. [automated] Run CI pipeline on the release commit - Ensure the HEAD commit (`f7a4f1c`) passes the GitHub Actions workflow `build.yml`. The workflow must complete with status `success` before tagging. Command (GitHub CLI): `gh run list --branch main --limit 5` and confirm the latest run is green. If not, block the release and fix CI first.
3. [manual] Verify local build - On the target release machine (or a clean container matching the CI toolchain), run:
```
git clone https://github.com/PawExperiences/BB.Project1.git
cd BB.Project1
cmake -B build && cmake --build build
./build/prime_tester 7 4
echo $?
```
Expected: `7 is prime` and `4 is not prime` on stdout, exit code `0`.
4. [manual] Smoke-test the executable against acceptance criteria - Run the following checks manually or via the CI test harness:
- `./build/prime_tester 2 3 4 97 7919` → all lines correct, exit 0.
- `./build/prime_tester abc` → stderr `not a number: abc`, exit 1.
- `./build/prime_tester 5 xyz 7` → stdout `5 is prime` + `7 is prime`, stderr `not a number: xyz`, exit 1.
- `echo -e '2\n3\n4' | ./build/prime_tester` → three lines, exit 0.
- `echo -n '' | ./build/prime_tester` → no output, exit 0.
- `./build/prime_tester 99999999999999999999` → stderr overflow message, exit 1.
5. [manual] Review bundled file set - Confirm the repository contains exactly: `CMakeLists.txt`, `src/prime.h`, `src/prime.cpp`, `src/main.cpp`, `README.md`, `.github/workflows/build.yml`, and `test/sample-pr.txt`. The last file was added by commit 800094b — confirm with the team it is intentional and acceptable in the release. No other source files should be present.
6. [automated] Create and push annotated release tag - ```sh
git tag -a v0.1.0 f7a4f1c -m "Release e2e prime tester 0.1.0 -- initial release"
git push origin v0.1.0
```
This tags exactly the feature merge commit. Do NOT force-push or rewrite history.
7. [automated] Build release artifact - CI will build automatically on tag push. Alternatively, build locally:
```sh
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build --config Release
```
Artifact: `build/prime_tester` (Linux/macOS) or `build/prime_tester.exe` (Windows).
8. [automated] Create GitHub Release and upload artifact - Using GitHub CLI:
```sh

  --title "e2e prime tester 0.1.0" \
  --notes-file release/RELEASE_NOTES.md
```
If running on Windows, replace `build/prime_tester` with `build/prime_tester.exe`. The `--notes-file` should contain the releaseNotes markdown from this runbook.
9. [manual] Verify GitHub Release page - Open https://github.com/PawExperiences/BB.Project1/releases/tag/v0.1.0 and confirm: release title, notes rendering, artifact download link, and tag commit hash all appear correct.

## Rollback

This is the initial release (no previous version exists). Rollback procedure:
1. Delete the GitHub release and tag `v0.1.0` from the GitHub Releases UI (do NOT force-delete the tag from the remote via git; use the UI or API to remove only the release and tag object).
2. If the release artifact was uploaded to GitHub Releases, remove it via the GitHub Releases UI.
3. No database migrations were applied; no data rollback is required.
4. If CI is broken by the build workflow, revert `.github/workflows/build.yml` by opening a PR that restores the previous file content (additive only — do not force-push).
5. Communicate to downstream consumers that `v0.1.0` has been retracted and no stable tag is currently available.
