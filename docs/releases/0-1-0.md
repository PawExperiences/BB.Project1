# e2e space invaders 0.1.0 (0.1.0)

## e2e space invaders 0.1.0

This is the inaugural release of **e2e Space Invaders** — a fully playable, zero-dependency browser Space Invaders clone built entirely with vanilla ES modules and the Canvas 2D API. No bundler, no server, no npm install required: open `index.html` from a `file://` URL in any modern browser and play.

### Highlights

- **Complete four-level campaign** — fight through the classic invader grid (Level 1), dodge enemy fire and a bonus UFO (Level 2), manage destructible shields and a split formation (Level 3), then face a two-phase boss with a health bar and escalating spread fire (Level 4).
- **Solid game-loop foundation** — fixed 60 UPS timestep with accumulator/delta-cap prevents catch-up bursts after tab backgrounding; clean Title → Playing → Game Over scene machine driven by Enter key alone.
- **Rich progression mechanics** — linear formation speed scaling, session-persistent shot count for UFO scoring, 2-second respawn invulnerability with visual flash, and an immediate phase transition when the boss hits half health.
- **Pure canvas rendering** — every entity (ship, invaders, bullets, UFO, shields, boss, HUD, health bar, explosions) is drawn with `ctx.fillRect`, `ctx.arc`, and `ctx.fillText`; zero external assets.
- **Green CI pipeline** — the BuildBoard-managed GitHub Actions workflow now references a valid Node LTS image and passes all build steps cleanly.

## Changelog

## [0.1.0] - Initial Release

### Added
- **Game Loop & Canvas Framework** (`index.html`, `game.js`, `gameConfig.js`): Fixed-timestep game loop at 60 UPS with accumulator/delta-cap pattern; three-scene state machine (Title → Playing → Game Over) driven by the Enter key; HUD rendering (score, lives, hi-score) drawn directly on canvas; exported `hudState` object for cross-module mutation; import stubs for all future modules.
- **Shared Constants** (`gameConfig.js`): `CANVAS_WIDTH`, `CANVAS_HEIGHT`, `PLAYER_SPEED`, `BULLET_SPEED`, `STARTING_LIVES`/`INITIAL_LIVES` exported as ES module named constants.
- **Keyboard Input** (`input.js`): `initInput()` attaches `keydown`/`keyup` listeners; `isKeyHeld(key)` reflects physical press/release state; OS key-repeat events suppressed via `event.repeat` guard.
- **Player Ship** (`player.js`): `Player` class with delta-time movement (ArrowLeft/a, ArrowRight/d), canvas-edge clamping, single in-flight bullet (Space), bullet auto-removal on exit, procedural canvas drawing, externally writable `lives` property.
- **Invader Grid & Collision** (`invaders.js`, `collision.js`): 11×5 formation (55 invaders) drawn with `ctx.fillRect`; sideways march with edge-detect-and-drop; pure `rectsOverlap(a,b)` AABB helper; `checkBulletVsInvaders` and `checkInvaderBulletsVsPlayer` passes; short-lived explosion effect (named-constant frame count); per-kill score increment (named constant); collision-before-draw ordering enforced in `game.js`.
- **Level 1** (`level1.js`): Classic invader wave; linear step-interval scaling 800 ms → 100 ms as kills accumulate; breach detection (formation reaches player row → lose life + reset formation); level-clear `CustomEvent('levelComplete', { detail: { nextLevel: 2 } })`; HUD level display via `hud.set('level', 1)`.
- **Level 2** (`level2.js`): Auto-advances from Level 1 via `advanceLevel()`; lives carried over; formation 1.5× faster than Level 1 at every threshold; random enemy fire (800–2000 ms interval, random column, bottom invader fires); enemy bullets at 300 px/s; UFO every 20 s alternating entry side at 120 px/s; UFO score tiers by `session_shot_count mod 4` (50/100/150/300); player hit → respawn at bottom-centre with 2 s invulnerability (flashing); lives-zero → Game Over scene; Enter on Game Over → Title.
- **Level 3** (`level3.js`): Four destructible shield bunkers (4×4 cell grids, ~8 px cells, ~80% canvas height); cell-level collision with player and enemy projectiles; descending invaders erode cells; 11×5 starting grid; formation split at 28th kill — columns 1–6 left half, columns 7–11 right half — each half sweeps independently in opposite initial directions; level-clear advances to boss.
- **Boss Level** (`boss.js`): 160×80 px boss drawn with canvas primitives at Y=60 px; proportional health bar at top of canvas; 90 px/s horizontal drift with edge reversal; Phase 1 (HP > 5): three-bullet spread every 1500 ms; Phase 2 (HP ≤ 5): spread every 700 ms, transition immediate; bullets at 260 px/s at 0°/±20° from vertical; collision via imported `checkCollision` from `collision.js`; boss projectile hit → sudden death, restart from Level 1; HP reaches 0 → win screen with final score and restart prompt.
- **CI Fix**: Updated `.github/workflows/build.yml` container image from invalid `node:330` to a valid Node LTS tag so the BuildBoard-managed pipeline passes.
- **README**: File-layout table listing all eight module files with owning card names; Manual Verification section for `file://` testing.

## Release steps

1. [manual] Verify CI pipeline is green - Open https://github.com/PawExperiences/BB.Project1/actions and confirm the latest workflow run on the main/master branch passes all steps. The `.github/workflows/build.yml` container image must reference a valid Node LTS tag (e.g. `node:20` or `node:lts`), not `node:330`. If the run is red, do not proceed — fix the workflow first.
2. [manual] Confirm build.yml toolchain matches this release - Open `.github/workflows/build.yml` in the repository. Confirm the container image tag is a valid, published Node LTS image (e.g. `node:20`). The build command must match the project's 'Node (no build step)' configuration — i.e. there is no compile step, the artifact_path is the repository root (all source files). If the build command, toolchain, or artifact path changed in this release, update the build resource config in BuildBoard so the workflow re-scaffolds and CI never drifts. This step is mandatory per release policy.
3. [manual] Run full manual smoke test - Follow every item in the manualSteps list above: open index.html via file://, exercise all four levels, boss phases, shield erosion, UFO scoring, respawn invulnerability, Game Over, and win screen. Record pass/fail for each checkpoint. Do not proceed if any checkpoint fails.
4. [manual] Update CHANGELOG and README for release - Ensure CHANGELOG.md (or the relevant section of README.md) contains the 0.1.0 entry. Confirm README.md Manual Verification section and file-layout table are up to date. Commit with message `docs: update changelog and README for v0.1.0` to the main branch.
5. [automated] Create and push the v0.1.0 git tag - Run the release script (see scripts section). It executes:
  git tag -a v0.1.0 -m "Release v0.1.0 – e2e space invaders initial release"
  git push origin v0.1.0
Do NOT force-push or overwrite an existing tag. If the tag already exists, abort and investigate.
6. [automated] Package the release artifact - The release script creates a zip archive of all source files (index.html, game.js, gameConfig.js, input.js, player.js, invaders.js, collision.js, level1.js, level2.js, level3.js, boss.js, README.md) named `e2e-space-invaders-0.1.0.zip`. Excludes .git/, .github/, and any node_modules/ directories.
7. [automated] Publish GitHub Release and upload artifact - The release script uses the GitHub CLI (`gh release create v0.1.0 e2e-space-invaders-0.1.0.zip --title "e2e space invaders 0.1.0" --notes-file RELEASE_NOTES.md`) to create the release and attach the zip. Requires `gh` authenticated with a token that has `contents: write` scope. RELEASE_NOTES.md should contain the releaseNotes markdown from this runbook.
8. [manual] Verify GitHub Release page - Open https://github.com/PawExperiences/BB.Project1/releases/tag/v0.1.0. Confirm: release title is 'e2e space invaders 0.1.0', release notes body is present, the zip artifact is attached and downloadable, and the tag points to the correct commit SHA.
9. [manual] Post-release CI check - The tag push will trigger a new GitHub Actions run. Wait for it to complete and confirm it is green. If it fails, do not retract the release immediately — investigate whether the failure is a flake or a real regression, then follow the rollback plan if necessary.

## Rollback

1. Since this is the initial release (no previous tag), a rollback means removing the v0.1.0 release artefact and tag from GitHub and communicating to users that the release has been withdrawn.
2. Navigate to https://github.com/PawExperiences/BB.Project1/releases, locate the v0.1.0 release, and use the GitHub UI to un-publish (convert to draft) or delete it — do NOT force-delete the tag from the remote; instead edit the release to draft status.
3. If the tag must be retracted, open an issue or contact a repository admin; do not force-push or delete remote tags directly (protected remote state rule).
4. Communicate the withdrawal in the project's communication channel with a link to the draft release and the reason.
5. If a hotfix is required, create a new branch from the commit at v0.1.0 (`git checkout -b hotfix/0.1.1 v0.1.0`), apply the minimal fix, and release as v0.1.1.
