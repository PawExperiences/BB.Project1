# e2e space invaders 0.1.0 (0.1.0)

## e2e Space Invaders v0.1.0

This is the **first playable release** of *e2e Space Invaders* — a browser-native, zero-dependency reimplementation of the arcade classic, running directly from a `file://` URL in any modern browser. The game is complete from the title screen through four increasingly difficult levels to a multi-phase boss fight and a win screen.

### Highlights

- **Full four-level progression** — Classic 11×5 invader grid (Level 1), return fire with respawn invulnerability (Level 2), destructible shield bunkers and a mid-level formation split (Level 3), and a two-phase boss with a health bar (Level 4).
- **Zero dependencies** — Pure ES modules, Canvas 2D API only; open `index.html` from disk with no server, no npm, no build step.
- **Fixed-timestep game loop** — 60-step/s update cadence with delta cap; smooth and tab-safe.
- **Persistent session state** — Score, hi-score, lives, and shot counter carry across all levels without a page reload.
- **Escalating difficulty** — Formation speed scales with surviving invader count; Level 2 is 1.5× faster; the boss doubles its fire rate at half health.
- **Green CI** — GitHub Actions build pipeline passing on merge; artifact uploadable via the GitHub Release engine.

## [0.1.0] - Initial Release

### Added
- **CI Scaffold**: Minimal `index.html`, `README.md`, and companion files committed to unblock the GitHub Actions build pipeline (`feat: CI build failed #158`).
- **Game Loop & Canvas Framework** (`game.js`, `gameConfig.js`, `index.html`): Fixed-timestep game loop at 60 steps/s with delta cap (≤250 ms), three-scene state machine (Title → Playing → Game Over) driven by ENTER key, on-canvas HUD (Score / Lives / Hi-Score), and exported `hudState` object (`feat: Game loop and canvas framework #159`).
- **Keyboard Input & Player Ship** (`input.js`, `player.js`): Hold-state keyboard tracker (`initInput` / `isKeyHeld`), procedurally-drawn player ship, single-bullet firing mechanic clamped to canvas bounds, lives initialised from `gameConfig.js` (`feat: Keyboard input and the player ship #160`).
- **Sprite Rendering & Collision Detection** (`invaders.js`, `collision.js`): 11×5 invader formation with horizontal sweep and drop logic, AABB collision (player bullet vs invader, invader bullet vs player), score increment (+10 per kill), 300 ms explosion effect, score overlay via `ctx.fillText` (`feat: Sprite rendering and collision detection #161`).
- **Level 1 – The Classic Grid** (`level1.js`): Playable first level; step-interval scales linearly from ~800 ms (55 invaders) to ~100 ms (1 invader); formation drops 48 px on edge contact; signals `'LIFE_LOST'` / `'NEXT_LEVEL'` / `null`; "LEVEL 1" drawn on canvas each frame (`feat: Level 1: the classic grid #162`).
- **Level 2 – They Shoot Back** (`level2.js`): Formation 1.5× faster than Level 1; single on-screen invader bullet fired from lowest invader in a random column every 800–2 000 ms; player respawn at bottom-centre with 2 s invulnerability and 200 ms flash; bonus UFO every 20 s at 120 px/s with score tiers [50,100,150,300] keyed by session shot count (`feat: Level 2: they shoot back #163`).
- **Level 3 – Shields & Formations** (`level3.js`): Four destructible 4×4-cell shield bunkers at ~80 % canvas height; standard 11×5 invader grid; formation splits into independent left/right halves when ≥28 invaders are destroyed; returns `'BOSS'` when all invaders cleared (`feat: Level 3: shields and formations #164`).
- **Boss Level – Multi-Phase Finale** (`boss.js`): 160×80 px Canvas-primitive boss drifting at 90 px/s; 10 HP health bar; Phase 1 (HP 10–6): 3-bullet spread every 1 500 ms; Phase 2 (HP 5–1): same spread every 700 ms at 260 px/s; sudden-death player rule; Win Screen on HP = 0 with final score and restart (`feat: Boss level: multi-phase finale #165`).
- **Supporting files**: `main.js` (entry-point wiring), `style.css` (dark-background canvas styling), `README.md` (planned file layout, manual verification steps).
- **CI Workflow** (`.github/workflows/build.yml`): BuildBoard-managed build workflow; re-scaffolded to match zero-build-step Node toolchain and artifact upload.

## Release steps

1. [manual] Confirm CI workflow currency - Open `.github/workflows/build.yml` and verify it matches the current toolchain: zero build step (no `npm run build`), artifact path is the repository root (or the documented `artifact_path`), and Node version matches any engine constraint in the project. This release ships no build-command change, so no update should be required — but a human must confirm this before tagging. If a drift is found, update the build resource config in BuildBoard so the workflow re-scaffolds correctly.
2. [automated] Run CI on release branch - Push the release branch (or confirm the feature PRs are merged to `main`). GitHub Actions triggers `.github/workflows/build.yml` automatically. Wait for a green check on the HEAD commit. Command (local confirmation): `git push origin main` — CI runs remotely.
3. [manual] Verify local smoke test (manual) - Open `index.html` directly from disk in Chrome and Firefox (`file:///path/to/repo/index.html`). Confirm: dark canvas, Title scene renders, ENTER starts Level 1, all four levels reachable, HUD updates, no console errors. This is the acceptance gate for the 'no server required' requirement.
4. [manual] Create and push the release tag - From the merged `main` HEAD, run:
```sh
git tag -a v0.1.0 -m 'Release v0.1.0 — e2e Space Invaders initial release'
git push origin v0.1.0
```
Do NOT delete or move existing tags. If the tag already exists from a prior attempt, stop and ask a human.
5. [automated] Package the release artifact - Run the release script (`release/scripts/release.sh` / `release.ps1` / `release.py`) to produce a zip archive of the shippable files: `index.html`, `game.js`, `gameConfig.js`, `input.js`, `player.js`, `invaders.js`, `collision.js`, `level1.js`, `level2.js`, `level3.js`, `boss.js`, `main.js`, `style.css`, `README.md`. Output: `dist/e2e-space-invaders-v0.1.0.zip`.
6. [manual] Create GitHub Release and upload artifact - In the GitHub UI navigate to Releases → 'Draft a new release'. Select tag `v0.1.0`. Set title to `e2e Space Invaders v0.1.0`. Paste the contents of `releaseNotes` (above) as the release body. Upload `dist/e2e-space-invaders-v0.1.0.zip` as the binary asset. Publish the release. Do NOT mark it as a pre-release unless the smoke test above failed.
7. [manual] Post-release verification - Download the published artifact from the GitHub Release page, unzip it, open `index.html` from disk, and confirm the game runs correctly end-to-end. Verify the release notes and changelog are visible on the GitHub Releases page.

## Rollback

1. **No server-side state or database exists** — this is a static browser game; there is nothing to roll back on the server side.
2. **Tag rollback (Git):** The previous state is the empty/reset repository (`8bd32b6 chore: reset repo`). To revert end-users to that state, re-point the GitHub Release to the prior commit or simply delete the v0.1.0 release and tag on GitHub (manual action in the GitHub UI — do NOT force-push or delete remote commits).
3. **Artifact rollback:** If the release artifact (zip of source files) was uploaded to the GitHub Release, remove the release (do not delete the tag history) via the GitHub Releases UI and re-upload the prior artifact.
4. **CI:** The `.github/workflows/build.yml` is BuildBoard-managed. If the workflow is broken by a bad config, revert the `build.yml` change via a new PR (additive fix — do not delete the file or the workflow run history).
5. **User impact:** Because the game runs from a local `file://` URL, any user who already downloaded `index.html` is unaffected. Communicate the rollback via release notes on the GitHub Releases page.
