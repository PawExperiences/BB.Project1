# todo-api v0.1.0

The first release of `todo-api`: a small Fastify + TypeScript service for managing a todo list in memory. This release stands up the full surface described in the project's kickoff scope — list, create, and delete — behind a layered routes → controllers → services → repositories architecture, with zod-validated input and a Vitest suite that exercises every route over real HTTP against a live server instance.

## Highlights
- `GET /todos` and `POST /todos` for listing and creating todos, plus `DELETE /todos/:id` for removing one.
- Zod validation on create (`title` must be a string) and on delete (`id` must be numeric), with predictable `201`/`400`/`204`/`404` semantics — non-numeric ids are treated as not-found, not as a bad request.
- TypeScript strict mode throughout, Fastify as the HTTP layer, in-memory storage — no database, driver, or migration step required to run this version.
- Full Vitest coverage that boots the real server on an ephemeral port for every test and tears it down in `afterAll`.
- README documents install/build/run commands and the request/response contract for all three endpoints.

## Changelog

## [0.1.0] - 2026-08-11

### Added
- Initial `todo-api` HTTP service: a Fastify server in TypeScript strict mode, structured as routes → controllers → services → repositories (`src/app.ts`, `src/index.ts`, `src/routes/todos.route.ts`, `src/controllers/todos.controller.ts`, `src/services/todos.service.ts`, `src/repositories/todos.repository.ts`, `src/schemas/todo.schema.ts`).
- `GET /todos` — returns all todos as a JSON array (`[]` on a fresh process).
- `POST /todos` — creates a todo from `{ "title": string }` (validated with zod); returns `201` with the created `{ id, title }` (auto-incrementing integer id starting at 1), or `400 { "error": "..." }` when `title` is missing or not a string.
- `DELETE /todos/:id` — removes a todo by numeric id; returns `204 No Content` on success. Both an unknown numeric id and a non-numeric id return `404 Not Found` (never `400` for a malformed id, by design).
- Fallback `404` for any path/method not covered by the routes above.
- In-memory, process-lifetime todo repository — no database or migrations in this release.
- Vitest suite (`tests/server.test.ts`, `tests/todos.route.test.ts`) that boots the app on an ephemeral port and drives it with real HTTP requests, covering list/create/delete, id assignment, validation, and the 404 fallback; server is closed in `afterAll`.
- `package.json` (`name: todo-api`, `type: module`) with build/start/test scripts, `tsconfig.json` in strict mode, and `README.md` covering install/build/run and the endpoint contract.

## Rollback

This is the initial release (PREVIOUS: None), so there is no earlier version of todo-api to roll back to. If a critical issue is found after publishing v0.1.0:
1. Never delete or force-push over the v0.1.0 tag, its GitHub release, or any commit — remote tags, releases, and history must not be removed, only added to.
2. Stop routing traffic to, or stop, the deployed process (e.g. `systemctl stop todo-api`, `pm2 stop todo-api`, or scale the running container/task to 0) so the broken build stops serving.
3. Storage is in-memory only, so there is no persisted data or schema to roll back — stopping or redeploying only discards the current process's in-memory todos, which is expected and safe.
4. Fix forward: branch from the last good commit, apply the fix, and cut a new patch release (e.g. v0.1.1) through this same runbook, publishing it as a new tag/release rather than editing v0.1.0.
5. If you must stop serving with no replacement ready yet, leave the process stopped and communicate the outage — do not remove the release, tag, or workflow to 'undo' it.
