# e2e changelog writer 0.1.0 (0.1.0)

## e2e changelog writer 0.1.0

This is the first tagged release of **e2e changelog writer**. It ships no application code -- it lays the documented, repeatable groundwork the project will use to track and publish every future change: a Keep a Changelog-formatted `CHANGELOG.md`, a step-by-step `RELEASING.md` checklist, and a `CONTRIBUTING.md` guide that teaches contributors to write changelog entries the way an end user would read them, not the way a commit message would. As a worked example, this release also walks `CHANGELOG.md` through its own release-cut checklist once, relocating the entries that were sitting under `[Unreleased]` into an illustrative `[0.2.0]` section inside the file -- that demonstrates the process working end to end; it is not a second real release. This tag, `v0.1.0`, is the only one being published today.

## Release steps

1. [automated] Confirm the three bundled PRs are merged to main - Run `gh pr view 324 --json state,mergedAt`, `gh pr view 325 --json state,mergedAt`, and `gh pr view 326 --json state,mergedAt` (or `git log --oneline -4`) and confirm all three show MERGED on `main`: e8fd6f3 (#324 'CHANGELOG and release checklist'), acb1d23 (#325 'A contributing guide that matches the changelog'), a6e6433 (#326 'A worked second release'), sitting on top of 8931e5b ('chore: reset for the next e2e project').
2. [automated] Verify CI is green on main - Run `gh run list --branch main --limit 5 --json headSha,conclusion` and confirm the run for commit a6e6433 (current HEAD) has conclusion `success` before proceeding.
3. [manual] Confirm the CI build workflow is current for this release's toolchain - This release ships no application code, so it introduces no new build command, language/runtime, or artifact path. Open `.github/workflows/build.yml` and the project's build resource config (command + artifact_path) side by side and confirm they still match. STRICT RULE: if any future release changes the build command, toolchain, or artifact path, update the build resource config first -- BuildBoard re-scaffolds build.yml from it -- so CI never silently drifts from what the project actually builds. Do not hand-edit build.yml.
4. [manual] Get maintainer sign-off to ship v0.1.0 - A human maintainer reviews this runbook's changelog/releaseNotes against the merged content of CHANGELOG.md, RELEASING.md, and CONTRIBUTING.md on main, and explicitly approves cutting v0.1.0.
5. [automated] Run the release script from a clean main checkout - From a clean, up-to-date checkout on `main`, save this runbook's `releaseNotes` to `release/notes/0.1.0.md`, then run `python3 release/scripts/release.py 0.1.0 --notes-file release/notes/0.1.0.md` (or the `.sh`/`.ps1` equivalent with the same arguments). The script verifies the worktree is clean, the branch is `main`, and CHANGELOG.md has a `## [0.1.0] - ` heading; then it creates annotated tag `v0.1.0`, pushes it to `origin`, and publishes the GitHub release via `gh release create`. It is idempotent -- rerunning it after a partial failure skips any step already completed.
6. [automated] Verify the published release - Run `gh release view v0.1.0` and `gh run list --branch main --limit 1` to confirm the release exists with the expected notes and that CI on the tagged commit is `success`.
7. [manual] Announce the release - Post the release link (`gh release view v0.1.0 --json url --jq .url`) to the project's usual announcement channel.

## Helper scripts (committed under release/scripts/)

- **release** `release/scripts/release.py` (python) -- Standard-library-only Python 3 script: verifies a clean git worktree, that you're on `main`, and that CHANGELOG.md has a `## [<version>] - ` heading, then creates annotated tag `v<version>`, pushes it to `origin`, and publishes the GitHub release via `gh`. Idempotent -- safe to rerun. Run once, from repo root, when a human maintainer has approved shipping the release: `python3 release/scripts/release.py 0.1.0 --notes-file release/notes/0.1.0.md`.
- **release** `release/scripts/release.sh` (sh) -- POSIX sh equivalent of release.py: verifies a clean git worktree, that you're on `main`, and that CHANGELOG.md has a `## [<version>] - ` heading, then creates annotated tag `v<version>`, pushes it to `origin`, and publishes the GitHub release via `gh`. Idempotent -- safe to rerun. Run once, from repo root, when a human maintainer has approved shipping the release: `sh release/scripts/release.sh 0.1.0 release/notes/0.1.0.md`.
- **release** `release/scripts/release.ps1` (powershell) -- ASCII PowerShell equivalent of release.py: verifies a clean git worktree, that you're on `main`, and that CHANGELOG.md has a `## [<version>] - ` heading, then creates annotated tag `v<version>`, pushes it to `origin`, and publishes the GitHub release via `gh`. Idempotent -- safe to rerun. Run once, from repo root, when a human maintainer has approved shipping the release: `powershell -File release/scripts/release.ps1 -Version 0.1.0 -NotesFile release/notes/0.1.0.md`.

## Rollback

This release only adds documentation files plus a git tag and a GitHub release -- there is no runtime artifact, service, or schema to roll back. Per protected-remote-state rules, never delete or force-move the v0.1.0 tag or its GitHub release. If the shipped content is later found to be wrong: (1) open a follow-up PR that fixes CHANGELOG.md, RELEASING.md, or CONTRIBUTING.md on main; (2) cut a new corrective release (e.g. 0.1.1) by following RELEASING.md's own checklist end to end, including its Unreleased-to-dated-section step; (3) if the v0.1.0 GitHub release notes themselves are misleading, edit them in place with `gh release edit v0.1.0 --notes-file <corrected-notes.md>` (edit, never delete) and point readers at the corrective release. RELEASING.md's own 'if the tag was pushed incorrectly' step documents this same human-in-the-loop recovery flow for maintainers going forward.
