# e2e unit converter 0.1.0

The first release of `units`, a small typed Python library for converting values between metric length units and between metric mass units. It ships one public function, `convert(value, frm, to)`, backed by data-driven conversion tables so adding a unit later is a one-line table edit rather than new code.

## Highlights
- `convert(value, frm, to)` converts between metric length units (m, km, cm, mm) and between metric mass units (g, kg, mg).
- Conversion factors live in one place, `src/units/tables.py`, as the single source of truth for both the library and its tests.
- Mixing dimensions (for example converting a length to a mass) raises a `ValueError` naming both units; an unrecognized unit code raises a `KeyError`.
- Results are unrounded floats: exact arithmetic, no hidden precision loss.
- Installable via standard PEP 517 tooling (`uv build` or `pip install .`); requires Python >= 3.12.
- Ships with a full pytest regression suite and a README unit/example reference.

## Examples
- `convert(1, 'km', 'm')` -> `1000.0`
- `convert(1500, 'g', 'kg')` -> `1.5`
- `convert(2.5, 'm', 'cm')` -> `250.0`

## Known limitation
This release supports metric units only (length: m, km, cm, mm; mass: g, kg, mg). Earlier grooming notes for this release also referenced imperial units (inch, ft, mile, oz, lb); per the conversion-tables task, that was superseded by a resolved clarification narrowing scope to metric-only, and the shipped `src/units/tables.py` reflects that metric-only set. If imperial support is still expected, it was not delivered in 0.1.0 and should be scoped as a follow-up task.

## Changelog

## [0.1.0] - 2026-08-11

### Added
- `units` package: a small, typed, PEP 517-installable library (`pyproject.toml`, `requires-python >= 3.12`) exposing `convert(value, frm, to)` for length and mass conversions.
- `src/units/tables.py`: single source of truth for conversion factors -- `LENGTH_FACTORS` (m, km, cm, mm, relative to metres) and `MASS_FACTORS` (g, kg, mg, relative to grams) -- imported by `src/units/__init__.py` rather than duplicated.
- `convert()` raises `ValueError` naming both units when asked to convert across dimensions (length vs mass), and `KeyError` naming the unknown unit for any unrecognized unit code.
- `convert()` returns the raw, unrounded float result of `value * (factor(frm) / factor(to))`.
- `tests/test_convert.py`: pytest suite covering round-trip conversions for each dimension, cross-dimension rejection, and unknown-unit rejection.
- `README.md`: supported-units reference grouped by dimension (Length: m, km, cm, mm; Mass: g, kg, mg) plus three worked conversion examples.

## Release steps

1. [automated] Confirm clean checkout at the release commit - From the repo root on branch main, run `git fetch origin` then `git status --porcelain` (expect empty output) and `git rev-parse HEAD` (expect it to resolve to baf6728, the tip of PR #262, 'Tests and the supported-unit list'). Abort the release if the tree is dirty or HEAD differs.
2. [automated] Install release tooling - Ensure python3 (>=3.12), pytest, ruff, and uv (or the build package) are on PATH; install anything missing with `pip install pytest ruff build` or install uv per its docs. These are release/dev tooling only, not runtime dependencies of the units package, and are not added to pyproject.toml.
3. [automated] Run the test suite - From the repo root run `python -m pytest -q`; the release blocks unless every test in tests/test_convert.py passes (round-trip conversions, cross-dimension rejection, unknown-unit rejection).
4. [automated] Run lint and format checks - Run `ruff check src tests` and `ruff format --check src tests`; both must exit 0, per the acceptance criteria on the 'The conversion tables' task.
5. [automated] Verify the shipped unit set matches the resolved spec - Import units and assert LENGTH_FACTORS keys equal {m, km, cm, mm} and MASS_FACTORS keys equal {g, kg, mg} (see release/scripts/release.py). This release bundle contains two conflicting task descriptions: 'Length and mass conversions' lists 11 units including inch, ft, mile, oz, lb, while 'The conversion tables' states a resolved clarification narrowing scope to the 7 metric-only units above, and requires __init__.py to import (not redefine) tables.py's dicts. This gate fails loudly, instead of silently shipping mismatched docs, if the installed package does not match the metric-only spec -- if it fails, STOP and have a human confirm which unit set is actually meant to ship before releasing.
6. [automated] Build distribution artifacts - Run `uv build` (falls back to `python -m build` if uv is not installed) from the repo root; expect dist/units-0.1.0-py3-none-any.whl and dist/units-0.1.0.tar.gz.
7. [manual] Confirm the CI build workflow matches this release's toolchain - Open .github/workflows/build.yml (BuildBoard-owned; re-scaffolded from the build resource's command and artifact_path) and confirm: the configured build command performs a PEP 517 build (for example uv build), the Python setup step targets >=3.12 (this release introduces requires-python = '>=3.12' in pyproject.toml for the first time), and artifact_path points at dist/ (the wheel and sdist built above). If the command, toolchain, or artifact path do not match, update the build resource's config in BuildBoard so build.yml re-scaffolds -- do not hand-edit the workflow file.
8. [manual] Release sign-off - A human collaborator reviews the changelog, release notes, and a green CI run for commit baf6728 on main, then approves proceeding to tag and publish (standard gate for the lazy-scrum flavour).
9. [automated] Tag the release - `git tag -a v0.1.0 -m 'e2e unit converter 0.1.0'` on main at baf6728, then `git push origin v0.1.0` (additive only -- no force-push, no history rewrite).

## Rollback

This is the project's first release (PREVIOUS: None) and the package is not deployed to any live service, so rollback risk is limited to containing a bad artifact, not undoing a running system.

1. Never delete the v0.1.0 git tag or the GitHub release -- remote history and releases must never be removed (protected remote state).
2. If a defect is found after publishing, edit the existing GitHub release body in place to add a clear Known issue notice pointing at the fix, instead of deleting or unpublishing it.
3. If the artifact was installed anywhere downstream, have consumers pin to not installing 0.1.0 until a patched 0.1.1 is released (there is no earlier good version to fall back to for a first release).
4. Cut a new patch release, 0.1.1, through this same runbook once the fix is groomed and merged; do not force-push or rewrite the v0.1.0 tag to point at new commits.
5. If distribution artifacts are ever uploaded to a package index, use that index's official yank mechanism (which hides but does not delete the version) rather than any delete operation.
