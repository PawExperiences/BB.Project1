# e2e word count 0.1.0 (0.1.0)

## wordcount v0.1.0

This is the first release of **wordcount**, a small Go command-line tool that reproduces the classic Unix `wc -l -w -c` counting behavior: point it at one or more files, or pipe data through stdin, and it reports line, word, and byte counts in a simple tab-separated format.

### Highlights
- Counts lines (`\n` bytes), words (`bufio.ScanWords` semantics), and raw bytes for each named file or stdin (`-`).
- Prints one line per input: `<lines>\t<words>\t<bytes>\t<name>`, plus a `total` line summing counts when more than one file is given.
- Byte-accurate: counts raw bytes read, not decoded runes, so multi-byte UTF-8 input is reported correctly.
- Resilient to bad input: a file that can't be opened is reported on stderr and skipped, without aborting the rest of the run; the exit code reflects whether any file failed to open.
- Counting logic lives in its own file (`count.go`) behind a single-pass `io.Reader` API, kept separate from the CLI argument handling in `main.go`.
- Covered by table-driven tests for the edge cases that are easiest to get wrong -- empty input, missing trailing newline, repeated spaces, and multi-byte UTF-8 -- with the exact expected output also published as a table in the README.

### Getting started
```
go build -o wordcount .
./wordcount go.mod main.go count.go
```
See `README.md` for the full usage reference and the output-format table.

## Changelog

## [0.1.0] - 2026-08-11

### Added
- Initial `wordcount` CLI: a Unix `wc`-style tool that counts lines, words, and bytes for named files or stdin (`main.go`, `go.mod`, module `wordcount`, `go 1.22`).
- Tab-separated per-input output `<lines>\t<words>\t<bytes>\t<name>` (`-` as the name for stdin), plus a final `total` line summing counts when more than one file argument is given (omitted for a single input).
- Per-file error handling: an unreadable named file is reported as `wordcount: <name>: <error>` on stderr and skipped, processing continues for the remaining files, and the process exits 1 if any file failed to open (0 if every input was processed cleanly).
- `README.md` documenting build/run usage and the output format.
- Table-driven tests (`count_test.go`) covering four edge cases: an empty reader, a single line with no trailing newline, a line with repeated/multiple consecutive spaces, and multi-byte UTF-8 input where byte count and rune count differ.
- `README.md` usage table showing the exact documented output for each of those same four cases, so tested and documented behavior share one source of truth.

### Changed
- Counting logic extracted out of `main.go` into its own file, `count.go`, which defines a `Counts` struct (lines/words/bytes) and an exported function that fills it from a single pass over an `io.Reader`. `main.go` now contains only argument/flag handling and calls into `count.go`. Pure internal refactor -- no CLI-visible behavior change (flags, output format, and exit codes are unchanged).

## Rollback

This is the first release (previous version: none), so there is no prior version to roll back to, and no server-side deployment to revert -- wordcount is a standalone CLI binary. If a defect is found after publishing: (1) do NOT delete the v0.1.0 git tag or GitHub release -- remote tags, releases, and history must never be removed; (2) mark the v0.1.0 GitHub release as a 'pre-release' via the GitHub UI so it is not surfaced as the recommended download, and note the known issue in the release description; (3) stop referencing/linking the v0.1.0 binaries from any install docs or download pages; (4) fix the issue and cut a fix-forward patch release (v0.1.1) following the same steps in this runbook, then point users to it; (5) if the defect stemmed from the build command, toolchain, or artifact path, correct the build resource config in BuildBoard first so v0.1.1's CI workflow re-scaffolds correctly before re-releasing. Anyone who already downloaded the v0.1.0 binary can simply stop using it or replace it with v0.1.1 once available -- no uninstall/migration steps are needed since the tool has no persistent state.
